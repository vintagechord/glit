# 온사이드 심의 데스크: 음원 가사 대조 (2026-11-26)

## 왜

멜론·지니 가사는 반복되는 후렴, 코러스, 메아리를 자주 빼먹는다. 심의 가사지와 심의폼에는 음원에서 불리는 가사가 반복 구절까지 모두 들어가야 한다.

2026-11-26 옥자 「꽃피는 내일 / 그 사람」 11곡 수동 음반 작업에서 음원을 직접 받아써서 대조했다. 그 결과 9곡 중 6곡에 문제가 있었다.

| 곡 | 발견한 문제 |
|---|---|
| 꽃피는 내일 | 2절 뒤 후렴 누락 |
| 달달한 라떼 | 2절 전체와 간주·엔딩 코러스 누락 |
| 똑똑똑 | 후렴 3회 중 2회만 있음, 2절 첫 두 줄이 실제 부른 것과 다름 |
| 더 없이 좋은 날 | 인트로 구절 누락, '가요 가요'로 적혔으나 실제로는 '달려가요' |
| 한잔 어때요 | 인트로·간주 코러스 누락 |
| 노란불 | '내 사랑에'로 적혔으나 실제로는 '나의 사랑에' |

이 작업을 데스크에서 반복할 수 있게 만든다. 자주 쓰는 기능은 아니므로 **관리자 수동 작업 → 음반**에만 둔다(사용자 결정).

## 목표

- 수동 음반 작업에 연결된 음원을 트랙별로 분석해, 현재 가사(문서 정보 수정 반영본)와 대조한 **제안 목록**을 보여준다.
  - **반복 구절 누락:** 음원에서 불렸는데 가사에 없고, 가사의 다른 곳에 같은 구절이 있다. 제안은 기존 가사의 표기를 그대로 가져온다.
  - **새 구절:** 불렸는데 가사 어디에도 없다(코러스 등). 받아쓴 글자를 제안하되 **확인 필요**로 표시하고, 반영 전에 글자를 고칠 수 있다.
  - **다르게 불림:** 가사의 한 줄이 음원과 다르다. 가사 표기와 받아쓴 표기 중 음원에 더 맞는 쪽을 점수로 비교한다.
  - **음원에서 들리지 않음:** 가사에 있는데 음원에서 찾지 못했다. 항상 확인 필요로 표시한다.
  - **알아듣지 못한 보컬 구간:** 보컬은 있는데 글자를 얻지 못했다. 글자 제안 없이 구간만 알린다.
  - **MR·연주곡 확인:** MR 트랙에서 보컬이 들리거나, 가사가 있는 트랙에서 보컬이 거의 없다.
- 제안마다 체크박스, 확신 정도(강함·보통·확인 필요), 시각, **▶ 재생** 버튼을 단다. 재생은 그 구간 1초 앞부터 시작한다.
- **선택한 제안 반영**을 누르면 문서 정보 수정의 가사(`local.overrides.tracks[].lyrics`)에 들어간다. 이후 심의 자료 생성은 기존 흐름 그대로다.
- 분석은 이 Mac에서만 한다. 음원을 외부로 보내지 않는다.

## 하지 않는 것 / 실패로 보는 것

- 온라인 신청, 뮤비, 작사·작곡 크레딧 대조는 하지 않는다.
- 관리자가 고르지 않은 가사 변경은 없다. 자동 반영도 하지 않는다.
- 띄어쓰기·문장부호·맞춤법만 다른 경우는 제안하지 않는다(소음 방지).
- 분석이 끝나지 않았거나 실패해도 자료 생성을 막지 않는다.
- 분석 도구를 몰래 설치하지 않는다. 관리자가 크기를 보고 설치 버튼을 누를 때만 내려받는다.
- 긴 분석이 다른 신청의 자료 생성·다운로드를 막으면 실패다. 대기열을 따로 쓴다.
- Intel Mac, Windows는 지원하지 않는다. 앱의 Node 런타임도 darwin-arm64다.

## 제약

- 데스크는 Node 서버(`server.mjs`)와 순수 JS 화면(`public/app.js`)으로 되어 있고, 앱에는 Node 런타임만 들어 있다. Python 모델(약 3GB)은 앱에 넣을 수 없다.
- 오늘 측정한 처리 시간(M 시리즈, 16GB)은 다음과 같다. 11곡(MR 짝 2곡 포함)이면 약 15분이다.
  - demucs 보컬 분리: CPU에서 곡당 약 75–95초. MPS에서는 `Output channels > 65536` 오류가 나서 CPU를 쓴다.
  - Whisper 받아쓰기: 곡당 15–25초.
- 오늘 정한 판단 규칙을 그대로 옮긴다.
  - 무음 환각 문구("감사합니다", "다음 영상에서 만나요", "한글자막 by …", "아멘")는 버린다.
  - 길게 끄는 음은 구절로 보지 않는다.
  - 후보별 강제 점수(log P)는 **빈 후보·짧은 후보 쪽으로 기우는 편향**이 있다(달달한 라떼 코러스가 실제로 있는데도 '없음'이 이겼다). 그래서 "없음" 판정에는 점수를 쓰지 않는다. 점수는 **같은 자리의 두 표기**를 비교할 때만 쓴다.
- 서비스 결과·이메일과는 무관하다. 다만 비회원 접수로 등록한 수동 음반이면, 가사를 반영할 때 기존 `syncOnline`처럼 온라인 접수에도 반영된다(기존 문서 정보 수정과 같은 동작).

## 검토한 방법

- **이 Mac의 Python 분석기를 Node가 구동 (선택).** mlx-whisper(large-v3-turbo)와 demucs(htdemucs)를 쓴다. 처음 쓸 때 데이터 폴더에 한 번 설치한다. 음원이 밖으로 나가지 않고, 보컬 분리로 정확도를 올리며, 강제 점수로 애매한 차이를 가린다. 비용은 설치 약 3GB와 곡당 1–2분이다.
- **클라우드 음성인식 API.** 설치가 없지만 음원이 외부로 나가고 분당 비용이 든다. 노래하는 한국어에 약하고 강제 점수도 없다. 제외했다.
- **whisper.cpp 단독.** 설치는 가볍지만 보컬 분리가 없고 점수 API도 없어 잘못된 제안이 늘어난다. 제외했다.

화면에서 결과를 다루는 방식은 **제안을 골라서 반영**으로 정했다(사용자 결정). 리포트만 보여주는 방식은 고칠 때마다 직접 타이핑해야 해서 제외했다.

## 설계

### 구성

| 파일 | 역할 |
|---|---|
| `tools/onside-desk/audio-check/worker.py` | 모델 작업만 한다. 디코딩, 보컬 분리, 받아쓰기, 보컬 에너지, 강제 점수. stdin/stdout JSON-lines로 명령을 받고 진행·결과를 낸다. 한 작업 동안 한 프로세스를 띄워 모델을 한 번만 올린다. |
| `tools/onside-desk/audio-check.mjs` | 판단 로직 전부. 도구 설치·상태, 음원↔트랙 연결, 정렬, 제안 생성, 반영. 순수 함수로 나눠 Node 테스트로 검증한다. |
| `server.mjs` | API와 전용 대기열. |
| `public/app.js` | 검토사항 탭 화면. |

`build-mac.mjs`의 복사 목록에 `audio-check.mjs`와 `audio-check/`를 넣는다.

### 분석 도구 설치

- 위치: `~/Library/Application Support/Onside Review Desk/음원분석/venv`. 설치 정보는 `음원분석/engine.json`(버전, 설치 시각, 패키지 목록)에 둔다.
- `uv`로 Python 3.12 venv를 만들고 버전을 고정해 설치한다.
  - 고정 버전: `mlx-whisper==0.4.3`, `demucs==4.1.0`, `torch==2.5.1`, `torchaudio==2.5.1`, `numpy==2.5.5`, `soundfile==0.14.0`, `imageio-ffmpeg`(버전 고정)
  - `uv` 위치: PATH, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, `~/.cargo/bin` 순서로 찾는다.
  - 없으면 설치하지 않고 "Homebrew로 `brew install uv` 후 다시 시도"를 안내한다.
- ffmpeg는 `imageio-ffmpeg`에 포함된 실행 파일을 쓴다. Homebrew ffmpeg에 기대지 않는다.
- 설치 작업은 모델도 미리 받는다(Whisper 가중치, htdemucs). 캐시는 각 라이브러리의 기본 위치를 그대로 써서 오늘 받은 모델을 다시 쓴다. 오늘은 둘 다 `~/.cache/huggingface`에 있다. *(내 결정: 다운로드 중복을 피하기 위해)*
- 오늘 시험 분석은 Homebrew ffmpeg를 썼다. 데스크는 다른 Mac 환경에 기대지 않도록 `imageio-ffmpeg`를 쓴다. *(내 결정)*
- 설치는 관리자가 **분석 도구 설치(약 3GB, 처음 한 번)** 버튼을 눌렀을 때만, 작업 대기열에서 진행 상황을 보여주며 한다. 실패하면 사유를 표시하고 다시 시도할 수 있다.
- 삭제 화면은 만들지 않는다. README에 폴더를 지우는 방법을 적는다.

### 음원 ↔ 트랙 연결

- 대상: 작업의 `attachments` 중 오디오 확장자(wav, mp3, m4a, aac, flac, aif, aiff, ogg).
- 자동 연결은 두 단계로 한다.
  1. 파일명 앞 번호를 본다(`^0?(\d{1,2})[ ._\-)]`).
  2. 번호가 없으면 곡명의 한글·영문 부분 일치로 찾는다.
- 같은 트랙에 파일이 둘 이상이면 무손실(wav·flac·aif)을 쓰고, 나머지는 "중복(사용 안 함)"으로 둔다.
  - 오늘 폴더에서는 07번이 mp3·wav 쌍이다. mp3는 wav를 MP3로 만든 같은 음원이었다.
  - 03·04·09번도 mp3와, 그 mp3를 변환한 wav가 함께 있다.
- 관리자가 드롭다운으로 바꿀 수 있고, 연결은 `item.audioCheck.mapping`(`{trackId: attachmentId|null}`)에 저장한다.
- MR 짝은 트랙 곡명이 "X (MR)/(Inst)/(Instrumental)"이고 같은 X의 보컬 트랙이 있으면 묶는다. 길이 차이가 0.5초 이내여야 한다.

### 분석 순서 (트랙마다)

1. **디코딩:** 모노 float로 바꾸고 첨부 파일의 sha256으로 캐시한다. 캐시 위치는 `신청별 자료/<id>/음원 대조/cache/<sha256 앞 16자>/`.
2. **보컬 분리:**
   - MR 짝이 있으면 원곡 − MR로 뺀다. 상호상관으로 시차를 맞추고 이득을 맞춘다.
   - 뺀 뒤 반주가 남은 정도가 −12dB보다 크면(마스터가 다른 경우) demucs로 바꾼다.
   - MR 짝이 없으면 demucs htdemucs `--two-stems vocals`를 CPU로 돌린다.
3. **보컬 에너지:** 0.25초 단위로 계산한다(곡 90퍼센타일 기준 dB).
4. **받아쓰기:**
   - 설정: mlx-whisper large-v3-turbo, `language=ko`, `condition_on_previous_text=False`, `word_timestamps=True`, `hallucination_silence_threshold=2`.
   - 버리는 구간:
     - 환각 문구 목록에 맞는 구간
     - 구간의 보컬 에너지 중앙값이 −35dB 미만인 구간
     - 같은 낱말이 6번 넘게 연속되는 구간
5. 결과(받아쓰기·에너지·분리 방식)를 캐시에 저장한다. 키는 `sha256`, 엔진 버전, MR 짝 sha256이다. 가사만 바뀐 재대조에서는 다시 분석하지 않는다.
6. **MR·연주곡 트랙:** 보컬 에너지 비율만 본다. MR 짝이 있으면 원곡에서 뺀 결과로 판단하고, 짝이 없으면 demucs로 분리한다. 보컬 프레임이 15%를 넘으면 경고한다.

### 대조와 제안 (Node, `audio-check.mjs`)

**정규화**

- 데스크 번역기가 가사에 넣은 번역 줄(`(번역: …)`, `manual-translation.mjs`)은 부르지 않는 줄이므로 대조에서 뺀다.
  - 반복 구절 누락을 넣을 때는 원본 블록에 딸린 번역 줄도 함께 복사한다. 문서에서 원문과 번역의 짝이 유지된다.
  - 가사만 저장하면 `lyrics_with_translation`이 비워지는 것(core.mjs)은 기존 문서 정보 수정과 같은 동작이므로 그대로 둔다.
- 영어 등이 섞인 줄도 대상이다.
  - 가사의 영문 글자가 40%를 넘는 트랙은 Whisper 언어를 고정하지 않고 자동 감지로 받아쓴다.
  - 이런 트랙은 결과에 "외국어 비중이 높아 정확도가 낮을 수 있음"을 표시한다. *(내 결정)*
- 한글·영문·숫자만 남기고 소문자로 바꾼다.
- 가사 글자마다 원래 줄 번호와 원문 위치를 기록한다.
- 받아쓰기 글자마다 시각을 기록한다(낱말 시각을 글자 수로 나눔).

**정렬**

- 가사 전체와 받아쓰기 전체를 **전역 정렬**한다(Gotoh 아핀 갭, Needleman–Wunsch).
- 점수 초기값: 일치 +2, 자모 유사 +1, 불일치 −1, 갭 시작 −3, 갭 연장 −0.5.
- difflib는 반복 구조에서 엉뚱하게 맞춰서 쓰지 않는다(노란불에서 47%).
- 곡당 수백 자이므로 typed array로 충분하다.

**차이 구간 모으기**

- 일치가 아닌 칸을 모은다. 일치 2자 이하로 떨어진 구간은 합친다.

**분류**

1. **받아쓰기에만 있는 6자 이상**
   - 가사 안에서 국소 정렬로 유사도 0.75 이상인 연속 줄을 찾으면 **반복 구절 누락**이다.
     - 넣을 위치는 가사 줄 경계에 맞춘다.
     - 원본 블록 앞에 빈 줄이 있었으면 빈 줄도 함께 넣는다.
     - 확신은 강함이다.
   - 찾지 못하면 **새 구절**(확인 필요, 받아쓴 글자, 수정 가능)이다.
   - 줄 안쪽에 끼어든 경우("괜찮나요 괜찮나요")는 아래 3번 **다르게 불림**으로 처리한다.
2. **가사에만 있는 6자 이상**
   - 해당 시간대 보컬 에너지가 충분하면 받아쓰기가 놓친 것으로 보고 제안하지 않는다. 오늘 사랑에게의 "불 꺼진 방안에"가 이 경우였다.
   - 에너지가 없으면 **음원에서 들리지 않음**(확인 필요, 삭제 제안)이다.
3. **양쪽 모두 있는 경우(바꿈)**
   - 받아쓴 쪽이 가사의 다른 줄과 0.75 이상 같으면, 그 줄 표기로 바꾸는 제안을 만든다(똑똑똑 2절).
   - 아니면 원래 줄과, 그 줄에서 차이 부분만 받아쓴 표기로 바꾼 줄을 후보로 둔다.
   - 둘 다 해당 구간(줄 시작 −0.5초 ~ 끝 +0.5초, 30초 이하) 보컬에 대해 **강제 점수**를 매긴다.
   - 점수 차 Δ(받아쓴 쪽 − 가사 쪽)로 판단한다.

     | Δ | 판정 |
     |---|---|
     | 8 이상 | 강함 |
     | 2 이상 8 미만 | 보통 |
     | 2 미만 | 제안하지 않음 |

     오늘 값: '달려가요' 23–25, 똑똑똑 2절 96, '나의 사랑에' 1.5–3.2, '괜찮나요' 반복 2–4.
   - **같은 줄이 여러 번 나오면 한 제안으로 묶는다.**
     - 반복 후렴처럼 같은 가사 줄에서 같은 차이가 반복되면 하나로 묶고, Δ 평균으로 판정한다.
     - 반영하면 해당하는 모든 줄을 바꾼다.
     - '나의 사랑에'(4곳 평균 약 2.6)는 보통으로 나와야 한다.
   - 강제 점수는 오늘 `score.py`와 같은 방식이다. 후보 토큰과 끝 토큰의 log P를 더하고, 창은 30초로 채운다. 임계값은 이 방식에서만 의미가 있다.
4. **알아듣지 못한 보컬 구간**
   - 보컬 에너지 −15dB 이상이 2.5초 넘게 이어지는데 받아쓰기 구간과 겹치지 않으면 알린다.
   - 단, 직전 받아쓰기 구간이 끝나고 1.5초 안에 시작하면 끄는 음으로 보고 제외한다.
   - 받아쓴 글자를 힌트로 보여준다.

**한 곳에 모아 둘 것**

임계값은 `THRESHOLDS` 상수 한 곳에 모은다. 오늘 11곡 결과로 맞춘 값이다.

**제안의 형식**

```js
{ id, trackId, kind: 'repeat'|'new'|'replace'|'unheard'|'unclear'|'instrumental',
  confidence: 'high'|'medium'|'check', start, end,
  op: { type: 'insertLines', afterLine, lines } | { type: 'replaceLine', line, from, to } | { type: 'deleteLines', from, to } | null,
  hint, score }
```

줄 번호는 분석 당시 가사의 `lyrics.split('\n')` 번호다.

### 저장

- `item.audioCheck`
  - `mapping`
  - `runs[]`: 최근 3개만 둔다. 내용은 `{ id, status, createdAt, finishedAt, engineVersion, tracks: [{ trackId, attachmentId, lyricsHash, separation, duration, status, error?, suggestions[], applied[] }] }`
- 받아쓰기 전문은 `신청별 자료/<id>/음원 대조/<runId>/result.json`에 둔다.
- 관리 백업(`backup()`)은 `음원 대조/cache`를 제외한다. 파생 음원이라 크기 때문이다.
- 휴지통 영구 삭제는 신청 폴더째 지우므로 함께 지워진다.

### API (수동 음반만, 아니면 400)

| 메서드·경로 | 동작 |
|---|---|
| `GET /api/audio-engine` | 설치 상태, 버전, `uv` 유무 |
| `POST /api/audio-engine/install` | 설치 작업을 대기열에 넣는다(`kind: 'audio-install'`) |
| `PATCH /api/cases/:id/audio-check/mapping` | 연결 저장 |
| `POST /api/cases/:id/audio-check` | 대조 작업(`kind: 'audio-check'`). 캐시가 있으면 정렬·점수만 다시 한다. |
| `POST /api/cases/:id/audio-check/cancel` | 진행 중인 worker를 종료한다 |
| `POST /api/cases/:id/audio-check/apply` | 아래 참고 |
| `GET /api/cases/:id/attachments/:attachmentId/stream` | Range 지원 재생. 오디오만 허용한다. |

`POST …/apply`의 입력은 `{ runId, items: [{ suggestionId, text? }] }`이다(`text`는 새 구절의 수정한 글자).

1. 트랙별로 현재 가사 해시가 분석 당시 `lyricsHash`와 같아야 한다. 다르면 409 "가사가 바뀌었습니다. 다시 대조하세요."를 돌려준다.
2. 줄 번호가 큰 것부터 적용한다.
3. 결과는 `validateLocalPatch`로 `overrides.tracks[{id, lyrics}]`에 저장한다.
4. 이어서 다음을 처리한다.
   - `sourceChanged` 표시
   - `reviewAcknowledgedRevision` 초기화
   - 감사 기록 "음원 대조 제안 n개 반영"
   - 비회원 접수로 등록된 작업이면 `syncOnline`

순서는 기존 `PATCH local`과 같다.

**대기열**

- 설치와 대조는 기존 `queue`(생성·다운로드)와 **별도의 직렬 `audioQueue`**를 쓴다.
- 작업 메시지로 진행을 알린다. 예: "5/11 보컬 분리 중 · 05 달달한 라떼로 주세요"
- 서버는 launchd 에이전트로 창과 별개로 돈다. 그래서 창을 닫아도 분석은 계속된다.
- worker는 다음 경우에 종료한다.
  - 취소
  - 서버 종료(`desk.close()`)
  - 작업 실패

- 도구가 없으면 위 내용 대신 설치 안내와 버튼을 보여준다.
- 강함은 기본 체크, 보통·확인 필요는 기본 해제다.
- 반영한 제안은 "반영됨"으로 표시한다. 가사가 바뀐 트랙에는 "가사가 바뀌어 다시 대조가 필요합니다 [다시 대조]"를 표시한다. 다시 대조는 캐시 덕분에 1분 이내다.
