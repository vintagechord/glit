# 심의 장바구니와 주문내역

`/mypage/cart`는 작성 완료된 `UNPAID` 신청서 중 `current_order_id`가 없는 항목만 표시한다. 신청서 저장은 결제 요청을 생성하지 않는다. `/mypage/orders`는 결제 수단을 선택한 뒤 생성된 주문과 과거 결제 이력을 표시한다. 영문 경로는 `/en`을 붙인다.

## 저장 구조와 상태 전이

- `submission_orders`: 주문 소유자, 결제 수단, 총액, 상태, 생성·입금확인·반환 시각.
- `submission_order_items`: 주문 당시 신청서 제목·패키지·가격·파일 ID의 스냅샷. 신청서를 삭제해도 `submission_ref`와 스냅샷은 남는다.
- `submission_payments`: 기존 PG 결제 시도 기록. `checkout_order_id`로 주문과 연결한다.
- `submissions.current_order_id`: 현재 신청서를 관리하는 주문. 결제 실패·취소만으로 이 연결을 해제하지 않는다.

카드·무통장·PayPal 주문 생성 RPC는 신청서를 잠근 뒤 주문 및 스냅샷 생성과 결제 대기 전환을 같은 트랜잭션에서 처리한다. 카드·PayPal 승인 및 종료 결과는 주문 상태에도 반영한다. 무통장 입금 확인은 주문의 모든 신청서를 함께 처리한다.

고객이 미결제 주문을 **장바구니로 돌리기**로 반환하면 기존 주문 이력은 유지하고 신청서의 연결만 해제한다. 다시 결제할 때 새 주문이 생성된다. 반환 시 소유권, 전체 묶음, 입금·승인 여부, 심의 시작 여부를 DB 잠금 아래 재검증한다. 결제 창이나 다른 탭의 오래된 요청이 새로운 주문의 상태를 덮어쓸 수 없다.

## 결제 결과 확인

Inicis 승인 요청 전에 단일 처리 권한을 확보한다. 중복 콜백은 외부 승인 API를 다시 호출하지 않는다. 승인 요청 이후 통신 오류 등으로 결과를 확정할 수 없으면 `APPROVAL_UNCERTAIN` 및 `REVIEW_REQUIRED`로 보존한다. 이 경우 고객의 반환·재결제를 허용하지 않으며 PG 거래와 DB의 실제 결과를 대조해야 한다. 승인 DB 응답이 유실됐다는 이유만으로 외부 결제를 취소하지 않는다.

이전 신청서의 상태 변경 API는 HTTP 410을 반환하고, 구 결제 페이지는 소유권을 확인한 뒤 장바구니 또는 주문내역으로 이동한다.

## 접근 권한과 기존 자료

회원 주문은 로그인 사용자 ID로 조회한다. 비회원은 주문에 포함된 모든 신청서의 정확한 조회 코드를 제시해야 한다. 조회 코드는 장바구니와 별도 브라우저 저장소에 보존하며 API 응답에는 코드나 해시를 반환하지 않는다. 신청서 삭제 후 이력 조회에는 주문 당시 코드의 SHA-256 해시를 사용한다.

0097은 기존 PG 기록과 실제 신청서 결제 상태를 이관한다. 근거 없는 과거 묶음이나 결제 시각을 추정하지 않으며 충돌하는 자료는 확인 필요로 표시한다. 과거 기록의 항목 설명은 이관 당시 자료임을 표시한다. 0098은 Inicis 승인 처리 권한 및 불확실한 결과 보존을 추가한다.

## 검증

`scripts/submission-orders-sql-test.sh`는 운영 접속 정보 없이 격리 PostgreSQL에서 마이그레이션과 상태 전이를 검증한다. `tests/submission-orders*.test.ts`는 소유권·조회·반환 HTTP 계약을 검증한다. `tests/e2e/submission-cart-checkout.spec.ts`는 장바구니와 주문내역 UI를 검증하며 결제·반환 요청은 모의 응답을 사용한다. 실제 PG 결제나 고객 입금 상태 변경은 테스트로 실행하지 않는다.
