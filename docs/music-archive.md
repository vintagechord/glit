# 내 음악 관리 — 구현 및 운영 안내

> 최신 국내 검색·실제 앨범 가져오기와 초성 제안은 [2026-09-08 후속 변경](music-archive-domestic-update.md)을 참고하세요. 아래 기존 배포 기록의 MusicBrainz 기본 검색/회원 권한 카드 설명은 후속 변경으로 대체됩니다.

확인일: 2026-09-08. 사용자의 운영 반영 승인에 따라 Supabase 운영 DB에 0095를 적용하고 Render `glit`의 main 자동 배포를 완료했다. 최종 코드 `9eff20a`의 실제 저장·조회·증빙 검증도 통과했다. 상세 결과는 [운영 배포 기록](music-archive-deployment.md)에 있다. 외부기관 신청·결제·음악 제공처 이용 계약은 수행하지 않았다.

## 진입과 사용

- 회원: 마이페이지 → **내 음악 관리** (`/mypage/music`). `/dashboard/music`에서도 진입한다.
- 아티스트를 직접 추가하거나, 검색 후보의 이름·구분 정보·출처를 비교하여 연결한다. 제공처 URL 연결은 본인·권리자 인증이 아니다.
- 아티스트 → 발매작 → 트랙을 선택한다. 앨범/EP/싱글/참여작·연도 필터, 직접 추가·수정, 서비스 링크, 제외·복구를 제공한다.
- 심의 / 저작권 등록 / 실연자 등록 / 노래방 등록에서 필요한 기관과 대상 트랙을 선택한다. 상태, 결과, 기록 출처, 자동 조회 상태는 서로 다른 값이다. 선택 트랙 일괄 입력은 적용 미리보기를 거친다.
- 음악저작물 관리와 법적 저작권 등록은 별도 업무다. 가입·신탁 및 실연자 위탁 관계는 아티스트의 별도 가입 관계 기록에서 관리한다. TJ·금영과 참여자별 업무도 각각 기록한다.
- 공식 안내를 읽고 외부 사이트에서 직접 신청한 뒤, 접수번호·곡번호·날짜·메모를 기록한다. 링크 방문은 업무 상태를 바꾸지 않는다. 기관 비밀번호·인증서·신분증을 보관하지 않는다.
- 기존 심의는 **기존 내역 연결**에서 본인 접수만 검색한다. 트랙 연결 시 원본 접수의 대응 트랙까지 선택한다. 결과와 파일은 원본 접수를 조회하며, 연결 해제는 원본을 삭제하지 않는다.
- 중복 비교 후 병합하면 원본을 보존하고 대표 항목에 연결한다. 합쳐진 항목의 기록을 다른 녹음에 복사하지 않는다. 복구로 연결을 해제할 수 있다.

## 기존 시스템 조사와 재사용

현재 저장소는 Next.js 16.3.1 App Router, React 19, Zod 4, Supabase Auth/Postgres, B2 파일 저장소를 사용한다. `node_modules/next/dist/docs`의 Route Handlers·Mutating Data·after 문서를 읽고 구현했다.

- `profiles.user_id`, 검증된 Supabase `auth.getUser()`, `is_admin()`을 사용한다. 회원별 API에서 인증 후 소유권을 다시 검사한다.
- 기존 `artists`는 이름 유일 제약이 있어 새 관리 목록의 동명이인 식별에 사용하지 않는다. 기존 데이터와 이름 연결은 변경하지 않았다.
- `submissions`, `album_tracks`, `station_reviews.track_results_json`, `submission_events`의 실제 관계를 재사용한다. 새 기능에는 주문·심의·결제 생성 코드가 없다.
- 기존 관리자 방송사 결과 저장 흐름을 변경하지 않았다. 회원 화면은 DB의 최신 원본을 `no-store`로 읽는다. 아카이브의 녹음 버전과 심의 트랙 ID를 명시적으로 대응시키며 제목·트랙 순서만으로 결과를 상속하지 않는다.
- 기존 `DashboardShell`, 색상·간격·모바일 카드 형태, 기존 심의 신청 페이지와 파일 다운로드 권한 경로를 재사용한다. 심의 신청은 기존 확인·자료 제출·결제 흐름을 그대로 거친다. 자동 주문이나 자동 사전입력 제출은 없다.
- 기존 review-docs의 비공개 B2 확인·업로드·다운로드 함수를 재사용한다. 기존 이메일·결제·알림 서비스는 호출하지 않는다. 재확인일과 보완 요청은 회원 화면에 표시한다.
- 기존 백그라운드 문서 작업과 같은 Postgres 작업 행·기한 있는 점유 방식으로 구현했다. 별도 클라우드나 유료 큐를 추가하지 않았다.

## DB 변경

추가 마이그레이션: `supabase/migrations/0095_music_archive.sql`. 기존 테이블 초기화·재생성·심의 결과 복제를 하지 않는다.

| 테이블 | 용도 |
| --- | --- |
| `music_archive_libraries` | 회원별 아티스트 관리 문서, 낙관적 버전, 제외 상태 |
| `music_archive_sources` | MusicBrainz 공개 메타데이터 스냅샷. 회원 메모·업무·관리 대상 판단을 넣지 않음 |
| `music_archive_jobs` | 제공처, 아티스트 ID, 수집 커서·범위·개수, 오류, 재시도 시각, 작업 점유 |
| `music_archive_events` | 행위자·시각·변경 버전·수정 내용의 비공개 감사 기록 |
| `music_archive_attachments` | 회원/아티스트/업무별 비공개 파일 참조 |
| `music_archive_guide_overrides` | 관리자가 수정한 기관 공식 링크·설명·확인일·노출 설정 |
| `music_archive_provider_limits` | 여러 프로세스가 공유하는 MusicBrainz 호출 간격 |

아티스트 단위 JSON 문서 안에 `releases`, `tracks`, `recordings`, `works`를 각각 독립적인 ID 배열로 둔다. 트랙은 특정 발매본의 디스크·수록 순서이며 `recordingId`를 참조한다. 녹음은 여러 `workIds`를 참조할 수 있다. 같은 녹음의 여러 앨범 수록, 같은 저작물의 다른 녹음 버전을 구분한다. 업무는 구체적인 트랙·기관·참여자·녹음/저작물 범위를 가진다.

이 구조는 기존에 아카이브용 발매본/녹음/저작물 정규 테이블이 없는 상황에서, 회원 수정·복구·동기화의 원자적 저장을 위해 선택한 최소 구조다. 서버에서 모든 참조와 값 범위를 검증하고 DB에서 소유자·버전·용량·쓰기 권한을 검사한다. 대규모 음악 지식 그래프나 조직 권한 시스템은 추가하지 않았다.

회원 클라이언트의 직접 DB 쓰기와 RPC 실행 권한은 차단한다. 읽기는 소유자 RLS를 적용하고, 공개 출처 및 공식 안내만 별도로 읽을 수 있다. 관리자는 작업 오류 요약·재시도·공식 안내를 관리하며 아티스트 이름으로 다른 회원의 비공개 업무를 찾아 공유하지 않는다.

서비스 전용 RPC가 문서와 감사 기록을 함께 저장한다. `commit_music_archive_step`은 버전·작업 점유·현재 제공처 연결을 검증하고 문서와 커서를 한 트랜잭션으로 저장한다. 오래된 작업은 변경된 사용자 문서를 덮어쓸 수 없다.

## 제공처와 공식 안내

상세 공식 출처·확인 시각·인증·상업 이용·표시/저장 조건은 [제공처 조사](music-archive-providers.md)에 정리했다.

| 제공처 | 코드 | 현재 활성화/실제 검증 |
| --- | --- | --- |
| MusicBrainz | 후보 검색, ID 조회, 발매본·참여작 페이지 수집, 전체 트랙 정규화·커서 재개 | 상업 API 이용 허가 및 User-Agent 설정 필요. 실제 단일 아티스트 HTTP 200 확인. 실제 검색·참여작은 12초 타임아웃; 전체 카탈로그 실증 미완료 |
| Spotify | 공식 URL 연결·수동 관리 | 공식 API 존재와 별개로 운영 접근·아카이브 저장 정책 확인 필요. 수집 어댑터 미구현·비활성 |
| 멜론·지니·벅스 | 공식 URL 연결·수동 관리 | 허용된 공식 아카이브 API/제휴 접근 미확인. 기존 사이트 파서·비공개 API를 새 수집에 사용하지 않음 |
| KOMCA·KOSCAP·저작권위원회·실연자연합회·TJ·금영 | 실제 읽을 수 있는 공식 방법 안내·검색/신청 링크·업무 기록 | 자동 등록 조회 API 미연동. 직접 입력은 사용자 입력/사용자 증빙으로 표시 |

동기화 완료는 해당 MusicBrainz API에서 조회한 범위의 처리 완료이다. 미등록 발매·지역 제한·누락 크레딧·세션 관계만 있는 참여작·다른 제공처까지 모두 검증했다는 의미가 아니다. 이미지·음원·가사 전문은 수집하지 않는다. 표지 대신 기본 음악 아이콘을 사용한다.

## 설치와 설정

1. 해당 배포 대상의 기존 마이그레이션 적용 상태를 확인하고 승인된 배포 절차에서 `0095_music_archive.sql`을 적용한다. 새로운 마이그레이션은 한 번 실행하는 형태다. 운영에서는 기존 DB를 reset하지 않는다.
2. 기존 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`를 사용한다. 새 음악 API 키를 브라우저에 주입하지 않는다.
3. 수동 관리에는 음악 제공처 키가 필요하지 않다. MusicBrainz 운영 활성화는 허가를 확인한 후에만 다음 서버 환경변수를 설정한다.

```dotenv
MUSICBRAINZ_COMMERCIAL_USE_APPROVED=true
MUSICBRAINZ_USER_AGENT=Onside/1.0 (https://실제서비스도메인/연락처)
```

환경변수는 허가를 얻는 절차가 아니다. 이번 작업에서는 해당 값을 실제 환경에 추가하거나 이용 계약을 체결하지 않았다.

4. 증빙에는 기존 B2 설정과 비공개 버킷을 사용한다. `REVIEW_DOCS_B2_BUCKET`이 있으면 해당 버킷, 없으면 `B2_BUCKET`을 사용한다. `b2_list_buckets` 확인 권한 및 `allPrivate` 상태를 실제 조회하고 업로드한다. 확인 실패 시 파일 기능만 제한하며 업무 텍스트 저장은 가능하다.
5. 요청 응답 후 `after()`가 최대 15단계/약 45초 범위의 수집을 수행한다. 시간 제한이나 프로세스 종료 후 커서는 DB에 남는다. 회원의 **이어서 수집**으로 재개할 수 있다. 페이지 조회 자체는 외부 제공처를 호출하지 않는다.
6. 화면을 닫아도 지속 처리할 운영이 필요하면 기존 서버/작업 환경에서 다음 워커를 실행한다. 새 호스팅 구매는 수행하지 않았다.

```bash
npm run music-archive:worker
# 배치/기존 스케줄러에서 한 단계만 처리할 경우
npm run music-archive:worker -- --once
```

워커와 웹은 같은 Supabase 및 제공처 설정을 사용한다. 기존 review-docs 워커를 대체하지 않는다. 잠든 무료 호스팅에서 계속 실행됨을 보장하지 않는다. 재시작 시 만료된 90초 점유를 회수한다. 네트워크/한도 오류는 대기 시각을 지키며 연속 3회 이후 수동 재개 상태로 남긴다. 모든 프로세스의 외부 호출은 DB에서 최소 1.1초 간격으로 예약한다.

## 관리자와 장애 대응

- `/admin/music`: 제공처 제한 상태, 최근 수집 작업의 오류·개수·시각, 재시도, 공식 안내 편집. 관리자 권한은 서버에서 다시 확인한다.
- `MIGRATION_REQUIRED`: 대상 환경의 0095 적용 및 PostgREST 스키마 반영 여부를 확인한다. 이번 코드만 배포하고 DB가 준비되지 않으면 저장 성공처럼 표시하지 않는다.
- `VERSION_CONFLICT`: 회원이 새로고침한 뒤 수정한다. 다른 창의 변경과 수집 기록을 조용히 덮어쓰지 않는다.
- `permission_required`/`configuration_required`: 허가·설정을 확인한다. 안내와 수동 기록을 계속 사용할 수 있다.
- `temporary_error`/`rate_limited`: 표시된 대기 이후 이어서 수집. 이미 저장한 앨범·트랙은 보존된다. 검색 결과 없음은 미등록 판정이 아니다.
- 연결 교체 시 이전 아티스트 수집 작업을 취소한다. 이전에 가져온 발매작과 업무 기록은 남으므로 비교 후 제외·복구 기능으로 정리한다.
- 원본 심의 삭제·권한 변경 시 연결을 미확인으로 표시한다. 다른 회원의 접수로 대체하거나 대기 결과로 재저장하지 않는다.
- 파일 서비스 장애 시 메모·번호·날짜를 먼저 저장한다. 증빙은 5MB 이하 PDF/PNG/JPEG이며 다운로드에 매번 회원 권한을 검사한다. 파일 첨부 자체는 기관 검증이 아니다.

## CSV와 한도

한 번에 최대 500행/400KB. 필수 머리글은 `release_key,release_title,track_key,track_title`이며 나머지 지원 열은 화면의 템플릿을 참고한다. `release_key`·`track_key`는 사용 권한이 있는 유통 자료의 안정적인 키를 넣는다. 제목으로 중복 판단하지 않는다. 외부 ID로 보장되지 않는 자체 키를 ISRC/ISWC로 만들지 않는다.

미리보기는 신규·중복·행별 오류를 표시한다. 오류가 있으면 전체 저장을 거부하고, 동일한 키로 재가져오기한 기존 항목은 보존한다. 같은 키의 제목·버전·저작물 정보가 충돌하면 확인하도록 한다. CSV로 주문·결제·외부기관 신청을 생성하지 않는다.

아티스트당 저장 문서는 최대 약 12MB, 발매작 5,000·트랙/녹음/저작물 각 50,000·업무 100,000개의 상한을 가진다. 회원별 활성 아티스트 30개, 보관 포함 전체 아티스트 300개와 증빙 100개를 제한한다. 목록은 DB에서 요약과 최근 발매작 12개만 반환하며 아티스트 20개씩 조회한다. 상세 문서는 한 아티스트 단위로 불러오므로 매우 큰 카탈로그는 향후 테이블 분할·서버 상세 페이지 분할이 필요할 수 있다.

## 검증과 현재 반영 상태

- 도메인/실제 어댑터 모의 응답/재동기화/CSV/원본 결과 연결 테스트는 `tests/music-archive-*.test.ts`에 있다.
- 실제 PostgreSQL 검증은 `tests/sql/music-archive.sql`. Docker가 준비된 로컬에서 `npm run music-archive:test:sql`로 임시 DB 생성·검증·정리를 재현할 수 있다. 운영 DB와 분리한 `postgres:17-alpine`에서 0095를 적용하고 소유권·버전·원자적 커서·작업 점유·공식 안내 권한·증빙 범위를 검증했다.
- UI 검증은 별도 모의 API/상태 저장소를 사용한 브라우저 테스트이며 실제 기관 신청이나 운영 회원 데이터 변경 테스트가 아니다.
- 최종 검증: 신규 도메인·어댑터·서버 보안 테스트 55개(Render 프록시 Origin 회귀 포함), 기존 인증·관리자 보호·심의 저장·결제 관련 회귀 테스트 49개 통과. 회원 브라우저 6개(390/1440px), 관리자 브라우저 2개(390/1280px) 통과. 실제 로컬 SQL 통합 검증, 프로덕션 빌드, TypeScript, 변경 파일 ESLint, diff 공백 검사도 통과했다. 브라우저와 API 단위 검증의 외부 서비스 응답은 모의 응답이며 운영 연동 검증으로 간주하지 않는다.
- 운영 DB dry-run에서 0095만 미적용임을 확인한 뒤 `supabase db push --linked --yes`로 적용했다. 로컬·운영 마이그레이션 기록 0095 일치, 재차 dry-run에서 미적용 없음, 새 테이블 7개와 목록 RPC HTTP 200을 확인했다. 기존 `submissions`와 `station_reviews` 조회도 정상이다.
- 기존 B2 버킷의 실제 `allPrivate` 설정 확인과 운영 PDF 증빙 업로드·다운로드 원본 해시 일치·삭제 검증을 통과했다. 실제 임시 회원 로그인 세션으로 아티스트·발매작·다른 녹음 버전 2개·단일 트랙 TJ 기록 저장 및 재조회를 검증했다. 해당 회원의 아카이브 행과 계정은 검증 후 삭제했다. 음악 제공처 수집이나 외부기관 신청 검증은 아니다.

재현 명령: `node --test --import tsx tests/music-archive*.test.ts`, `npm run music-archive:test:sql`, `npx playwright test --config=playwright.config.ts tests/e2e/music-archive.spec.ts tests/e2e/music-archive-admin.spec.ts --workers=1`, `npm run build`. 브라우저 테스트는 저장소의 실제 클라이언트를 독립적으로 번들링하며 운영 로그인 우회를 추가하지 않는다.

운영 웹은 기존 무료 인스턴스를 유지한다. 새 유료 워커나 호스팅을 개설하지 않는다. 코드 롤백이 필요하면 이전 Render 배포로 되돌리고 새 테이블과 0095 마이그레이션 기록은 보존한다.
